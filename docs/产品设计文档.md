## 1. 项目概述

### 1.1 定位

大学生上门家教的**信息撮合平台**。连接在校大学生(老师端)与需要家教的家长/学生(家长端)。

小程序的核心价值:**引流 + 自助匹配 + 减轻客服工作量**。所有交易均转线下,平台不涉及线上支付。

### 1.2 商业模式

**信息费模式,收费前置:**

```
家长选老师 → 订单生成(待老师确认)
→ 老师确认试课 → 双方引导添加客服微信(订单进入"待收费")
→ 客服线下微信收取信息费(先收费)
→ 客服人工发放双方完整联系方式 → 订单进入"试课中"
→ 线下试课
→ 试课通过:订单完成
→ 试课不过:退费 → 订单失败 → 需求回退(家长重新选老师)或需求关闭
```

**防跳单是商业模式生命线,核心原则:双方完整联系方式(手机号)永远只由客服人工发放,小程序内任何页面不展示完整手机号。**

### 1.3 核心设计原则

| 原则 | 说明 |
|---|---|
| 收费前置 | 先收信息费再给联系方式,不赊账 |
| 联系方式全程脱敏 | C 端只展示 `138****1234` 或完全不展示,完整号码仅后台可见 |
| 单向对接 | 老师向家长需求投递简历;家长不能主动联系老师。避免家长"找事儿",客服操作简单 |
| 双验证门槛 | 老师=学籍人工审核;家长=加客服微信人工判断。两端供给质量是平台生命线 |
| 评价/履约跟人走 | 评价与反悔记录挂在用户上,不挂单条简历/需求 |

## 2. 合规与主体

### 2.1 主体与类目

| 项 | 决策 |
|---|---|
| 小程序主体 | **个人主体**(免费) |
| 类目 | **教育信息展示**(个人主体教育类目下唯一选择) |
| 微信认证 | 不需要 |
| 线上支付 | **不做**。全站措辞避开"购买/支付/充值/课程销售",统一用"预约/对接/服务信息" |
| 小程序备案 | 必须(提前 2-4 周) |
| 域名 ICP 备案 | 必须(个人可备案),后端 API 走 HTTPS |
| 政策红线 | 双减政策:定位"教育信息中介服务",老师均为独立个人,不做机构入驻,不碰课程销售 |

### 2.2 隐私合规(审核硬性项)

- 《隐私政策》《用户协议》:页面可访问,声明手机号收集用途
- 小程序后台配置**用户隐私保护指引**(2023.9 起强制)
- 注销账号入口:用户申请 → 客服后台人工删数据
- 手机号数据库 **AES 加密存储**(密钥放服务器环境变量,不进代码库)
- 上门安全提示文案:需求单/订单页固定展示"首次对接建议家长陪同/公共场所试课"等免责提示
- 位置接口为申请制:模糊定位 `getFuzzyLocation`(个人主体可申请),精确 `getLocation` 审核严、可能被拒,**备选方案为按区筛选**

### 2.3 风险清单

| 风险 | 对策 |
|---|---|
| 微信审核对导流话术敏感 | 用官方客服会话 `open-type="contact"`,不放"扫码加我微信"话术 |
| 跳单 | 联系方式隐藏 + 收费前置 |
| 双减政策 | 信息中介定位,低调运营 |
| 上门安全 | 老师学籍审核 + 家长人工审核 + 免责提示文案 |
| 个人主体能力限制 | 拿不到 getPhoneNumber → 手机号表单自填;不支持支付 → 线下收费 |

## 3. 用户角色与权限

### 3.1 角色模型

**三身份并存模型**:一个微信用户可同时拥有游客、老师、家长三种身份(大学生群体天然存在两重身份)。

- 注册即得**游客身份**:浏览公开内容无障碍,不能发布任何东西
- **老师身份**:学籍审核通过后拥有;拥有后可发布简历、查看需求广场、投递申请
- **家长身份**:加客服微信审核通过后拥有;拥有后可发布需求
- **身份是拥有关系,可同时持有**:一个用户既是老师又是家长时,**可以同时发简历和需求**
- 小程序为**单端 + 双视图**:老师视图(需求广场/我的简历/我的订单/个人)、家长视图(简历广场/我的需求/我的订单/个人),个人页提供视图切换;未拥有对应身份时显示该身份的"去认证"引导
- 数据模型:user 表独立,parent 身份、tutor 身份为扩展表;身份由扩展表状态推断,无需切换开关
- **处罚边界(不连坐)**:身份级处罚只作用对应身份(老师 blacklist 不影响家长身份发需求;家长举报核实下架需求不影响老师身份投递);仅用户级封禁(status=1)两端全封(严重违规)

### 3.2 身份验证门槛

| 身份 | 验证方式 | 审核人 | 通过后获得的能力 |
|---|---|---|---|
| 老师 | 上传**学生证照片 + 学信网截图**,客服电话核验本人 + 学籍信息 | 客服人工 | 发布简历、查看需求广场、投递申请 |
| 家长 | **先添加客服微信**,客服通过朋友圈判断真人与真实需求 | 客服人工 | 发布需求 |

### 3.2.1 资料完善时机(登录零摩擦,发布前引导)

| 时机 | 动作 |
|---|---|
| 微信登录 | **静默注册**,只拿 openid,不强制任何资料;**首次进入弹身份选择(老师端/家长端)**,选定后进入对应视图;未认证前均为游客,浏览广场无障碍 |
| 家长点"发布需求" | 触发完善引导:① 加客服微信(审核门槛)② 手机号必填 ③ 昵称/头像选填(弹微信头像昵称一键带入,组件自带) |
| 老师点"发布简历" | 触发完善引导:① 认证材料(学生证+学信网)② 手机号必填 ③ 昵称选填 |
| 头像 | 简历头像**选填**(微信头像能力 chooseAvatar 一键带入);认证不再要求个人照片 |

- 老师审核通过后才可发布简历;**简历可见性与审核状态独立**(详见 §9.1):
  - 修改敏感字段(学校/学历/擅长学科)→ 触发重新审核,审核期间简历强制隐藏,审核通过自动恢复可见
  - 修改非敏感字段(自我介绍/家教经验/可授课时间)→ 不重新审核(走敏感词检测)
- 家长未加客服微信/未过审核 → 无法发布需求

### 3.3 可见性权限矩阵

| 内容 | 已认证老师 | 未认证老师/纯家长 | 客服(后台) |
|---|---|---|---|
| 简历广场(老师简历) | ✅ 可见 | ✅ 可见 | ✅ |
| 需求广场(家长需求) | ✅ 可见 | ❌ 不可见(家长视图无入口) | ✅ |
| 需求详情业务字段(科目/年级/区/时薪/时间/学生情况/备注) | ✅ 全部可见,不存在申请前不可见 | — | ✅ |
| 需求详细地址(小区级) | ❌ 前端不显示,线下加客服微信后客服发 | ❌ | ✅ |
| 自己的完整手机号 | ✅(编辑时) | ✅(编辑时) | ✅ |
| 对方的完整手机号 | ❌ 只显示脱敏,线下客服发完整号码 | ❌ | ✅ |
| 简历业务字段(学校/科目/区域/经验/介绍) | ✅ | ✅ 全部可见;老师详细地址前端不显示 | ✅ |
| 其他老师申请状态 | ✅ 自己的申请 | — | ✅ 全部 |

**需求广场可见性绑定认证状态,而非角色写死** —— 想偷看需求的家长必须伪造学籍通过人工审核,门槛足够。家长之间互相看不到对方的需求表(防比价、护隐私)。

## 4. 核心业务流程

### 4.1 老师侧(获取订单)

```
微信登录(静默)→ 游客 → 认证老师身份:完善资料(手机号必填/昵称选填)
+ 提交认证(学生证+学信网)
→ 客服电话核验 → 审核通过(拥有老师身份)→ 发布简历(审核通过后可见)
→ 浏览需求广场(筛选)→ 向需求投递简历(申请)
→ 家长选中 → 收到通知② → 确认试课 或 拒绝(记反悔)
→ 确认 → 双方加客服微信(订单待收费)→ 客服收费后发放联系方式
→ 线下试课
```

### 4.2 家长侧(获取老师)

```
微信登录(静默)→ 游客 → 认证家长身份:完善资料(手机号必填/昵称头像选填)
+ 加客服微信 → 客服审核通过(拥有家长身份)
→ 发布需求单(结构化字段)→ 等待老师申请
→ 收到通知① → 查看需求单关联的申请列表(红点角标)
→ 浏览简历、确定老师、选择 → 生成订单(待老师确认)
→ 收到老师确认/反悔通知 → 双方加客服微信 → 客服收费 → 线下试课
```

### 4.3 客服(核心人工环节)

```
审核老师(电话核验)→ 审核家长(朋友圈判断)→ 需求无人接单跟进
→ 老师确认后接收双方微信 → 收取信息费 → 发放双方联系方式
→ 试课结果确认 → 后台标记订单完成/失败(失败填责任方)
→ 家长放弃/后悔 → 管理端取消订单(收费过的走退费)
→ 差评审核、反悔申诉处理、封禁
```

## 5. 订单状态机

### 5.1 状态定义

| 状态 | 含义 | 所属阶段 |
|---|---|---|
| 申请中 | 老师已向需求投递简历,待家长选择 | 老师侧 |
| 待确认 | 家长已选中老师,订单生成,待老师确认是否去试课 | 订单 |
| 待收费 | 老师确认试课,双方添加客服微信,**等客服收取信息费** | 订单 |
| 试课中 | **已收费、已发放双方联系方式**,进入线下试课 | 订单 |
| 已完成 | 试课通过,客服后台标记 | 终态 |
| 试课失败 | 试课未通过,**已退费**,客服后台标记 | 终态(需求可再次流转) |
| 已取消 | 老师反悔 / 家长放弃(管理端取消,收费过的走退费) | 终态 |

### 5.2 状态流转与分支规则

```
老师投递简历 ──→ [申请中]
                    │ 家长选中(生成订单)
                    ▼
                 [待确认] ──老师拒绝(反悔)──→ [已取消] · 需求回退"待选择"
                    │                          · 保留其他老师申请,排除该老师
                    │ 老师确认                 · 该老师反悔次数 +1
                    ▼
                 [待收费] ◄── 双方加客服微信
                    │
                    │ 客服收费(线下微信)+ 发放双方联系方式
                    ▼
                 [试课中]
                    │
                    ├─试课通过,客服标记──→ [已完成]  · 需求单关闭
                    └─试课未通过,客服标记──→ [试课失败]
                                              · 客服线下退费(fee_status=2)
                                              · 与家长沟通:还要老师 → 需求回退"待选择",申请列表保留
                                                           不要老师 → 需求关闭(closed_reason=试课失败)
                                              · 失败必填责任方 fail_blame(老师问题/家长问题)+ 原因,审计追溯
                                              · 试课失败老师标记"已试课未通过",家长可再选
                                              · 其他老师视角:该需求从"已被接"变回可申请状态
```

**管理端取消分支(家长后悔/放弃):**

```
任意收费前状态 ──家长不要老师了,管理端取消──→ [已取消]
  · 需求关闭(closed_reason=家长放弃)
  · 填取消原因,留痕审计

[待收费] 之后 ──家长不要老师了,管理端取消+退费──→ [已取消]
  · fee_status=2(fee_refunded_at 记录)
  · 需求关闭(closed_reason=家长放弃)
```

### 5.3 反悔与撤销规则

| 场景 | 规则 |
|---|---|
| 老师撤回申请 | 家长未做选择前可撤回,**撤回后对该需求不可再次投递(终态)**——防重复投递,让老师三思;家长端申请列表同步更新,无惩罚 |
| 老师被选中后拒绝(反悔) | 记反悔次数 +1;家长收订阅通知 + 客服人工通知家长;需求回退,保留其他老师申请,**排除该老师** |
| 反悔 3 次 | 强制下架简历 + 禁止投递申请 |
| 反悔 3 次后恢复 | 向客服申诉 → 人工决定恢复 → 恢复后计数清零,后台保留历史记录 |
| 反悔次数可见性 | 仅老师个人中心可见自己的履约记录;简历不公开显示;影响排序 |
| 家长放弃/后悔 | **统一走管理端取消**:家长联系客服表达"不需要老师了" → 客服取消订单(填原因),收费前取消直接关单+需求关闭;收费后取消走**退费**再关单+需求关闭 |
| **老师确认时限** | 家长选中后**半天(12 小时)内**老师未确认 → **不自动取消**,由管理员催办:定时任务**每天 8:00**汇总所有超时未确认的订单,推送提醒管理员(后台待办 + 可选 Server酱推微信),管理员人工联系老师;老师拒绝或确认按正常分支处理 |
| 需求超时下架 | 发布后一周无人接单 → 后台提示管理员 → 管理员联系家长沟通 → 持续无人接单自动下架(**下架前再次提示管理员**) |

### 5.4 并发与数量规则

- 老师并发申请数:**不设限制**
- 需求接收申请数:**不设限制**
- 家长可发布需求数:多个
- **禁止自我成交**:同一用户的家长身份发布的需求,其老师身份**不可投递**(接口层校验 parent_user_id ≠ 自己);任何场景不允许自己与自己成交,防自导自演刷单刷评价

## 6. 通知设计(微信订阅消息)

### 6.1 机制约束

- 订阅消息免费、个人主体可用、模板需在 mp 后台申请(公共模板直接用,自定义模板审核 1-3 天)
- **一次授权 = 一条消息**;一次授权最多勾选 3 个模板(各获 1 条额度)
- 长期订阅仅医疗/政务/交通类目,教育类目**拿不到**
- 发送失败(额度用尽)返回错误码 `43101`,**静默忽略,不报错不重试**
- 订阅消息是"唤醒"手段;**站内信是"留痕"通道**:长文本(审核拒绝原因)、负向事件(排除/失效)、历史回看,订阅消息覆盖不了
- **站内信 = 系统 → 用户单向通知**,复用 yudao notify 体系(system_notify_template + system_notify_message,后台自带管理页);**用户间禁止互发**(私聊即跳单通道,红线)

### 6.2 通知与订阅埋点映射

| # | 通知内容 | 接收方 | 订阅埋点(前置授权) | 推送时机 |
|---|---|---|---|---|
| ① | 有老师申请了你的需求 | 家长 | **家长发布需求时**,打包订阅「申请提醒」+「对接提醒」 | 首个老师申请该需求时 |
| ② | 你的申请被家长选中 | 老师 | **老师提交申请时**,打包订阅「申请结果」+「对接提醒」 | 家长确认选择该老师时 |
| ③ | 老师已确认试课,请添加客服微信对接(待收费) | 双方 | ①和②打包订阅中各自剩余的「对接提醒」额度 | 老师确认试课后(订单进入待收费,与②的下游连发) |
| ④ | 老师已确认试课 / 老师拒绝了申请 | 家长 | **家长选中老师、生成订单前**,再订阅「订单状态提醒」 | 老师确认或反悔时(二选一,恰好 1 条额度) |

### 6.3 通知的克制原则

- **只通知被选中的老师**;未被选中的老师**不消耗任何通知额度**,自己去"我的订单"页面查看实时状态(红点角标引导)
- 管理员催办提醒不占用户订阅额度,走独立通道(后台待办 + 可选 Server酱)

### 6.4 多老师申请的聚合策略

- 第一个老师申请 → 立即推①,唤醒家长
- 后续申请 → **不推**,靠需求单申请列表的未读红点角标
- 后端每次申请都尝试发送,额度用尽收到 `43101` 静默忽略

### 6.5 补充通道

| 通道 | 用途 | 限制 |
|---|---|---|
| 客服消息(官方客服会话) | 用户主动进会话后 48 小时内可主动推送;收费、发联系方式、跟进对接 | 48 小时窗口 |
| **站内信(单向通知)** | **审核结果与原因(认证/简历/需求)、申请失效/排除通知、订单历史留痕、订阅消息兜底**;复用 yudao notify,个人页"消息"入口 + 未读角标 | 系统→用户单向,用户间禁互发 |
| 客服人工微信 | 停滞订单催办、异常通知兜底 | 人工 |
| 短信 | 重要节点兜底(如已匹配待对接) | 阿里云短信,个人签名审核麻烦,**MVP 不做** |

### 6.6 前端埋点规范

- 订阅授权必须**先于表单提交**:`wx.requestSubscribeMessage` 弹窗 → 用户允许 → 再提交
- 个人页提供**订阅消息重新授权入口**(用户拒绝订阅后可重新打开)

## 7. 评价体系

### 7.1 评价资格

订单进入**「试课中」之后**,双方各自获得对对方的一次评价权(终态为已完成或试课失败均保留评价权)。未进入试课中的订单(老师反悔拒绝、家长取消)不开放评价。

**评价对象是人(user),不挂单条简历/需求** —— 评价记录挂 `user_id`,任何简历卡片/需求卡片渲染时按人聚合;换简历、发新需求,历史评价跟着人走。

### 7.2 评价内容与可见性(不对称设计)

| 方向 | 内容 | 可见性 |
|---|---|---|
| 家长评老师 | 星级 + 标签(教学能力/沟通/守时/负责)+ 文字 | **公开**:老师详情页 + 简历卡片平均分 |
| 老师评家长 | 星级 + 标签(描述真实/守约/配合)+ 文字 | **仅客服后台可见** |

老师评家长不公开的原因:①防止老师间共享"难搞家长"黑名单;②防止家长看到低分后报复差评。其用途:客服匹配参考、多次差评的家长限制发需求。

### 7.3 防报复机制

- **差评(≤2 星)先人工审核**:进入"待客服确认"状态,客服决定公开或隐藏;被评人有申诉渠道
- 好评直接生效

### 7.4 评价与排序联动

老师默认排序公式(冷启动期评价稀疏,实际以最近活跃为主,公式预留):

```
平均评分降序 → 举报核实次数升序 → 反悔次数升序 → 最近活跃降序
```

举报核实次数与反悔次数均不公开显示(避免惩罚榜吓退老师注册),只影响排序与强制下架资格。

### 7.5 举报与内容风控

| 项 | 规则 |
|---|---|
| 举报方向 | 双向:家长举报老师 / 老师举报家长 |
| 举报原因分类 | 虚假信息、骚扰、人身安全、其他 |
| 举报入口 | 对方详情页、订单详情页 |
| 举报处置 | 举报后相关订单冻结,客服介入核实;**核实成立 → 强制下架其简历和需求(他人不可见)+ 举报核实次数 +1(影响排序),可申诉恢复**;驳回则无事 |
| 内容敏感词 | 自我介绍、需求备注、评价文字过**内置开源敏感词库**(MVP,不接第三方 API)+ 客服人工兜底 |

## 8. 定位与 LBS

### 8.1 定位策略

| 场景 | 行为 |
|---|---|
| 进入小程序 | `wx.getFuzzyLocation` 模糊定位拿城市 → 首页默认展示本城市数据,城市缓存 localStorage |
| 用户点"离我最近"筛选 | 弹授权拿精确定位 → 请求带经纬度 → 后端瞬时计算距离排序,**不落库** |
| 拒绝授权 | 回退:**Redis 前 50 条数据**(无城市筛选的全量最新数据);Redis 无数据时降级查**数据库最新前 50 条** |

### 8.2 数据落库规则

- **简历/需求表不存实时定位**。理由:①隐私红线(家长家址、老师实时位置);②定位是瞬时信息,简历是长期文档;③区域是服务范围概念
- 区域字段一律**手动选择**:
  - 简历:可授课区域(多选区,认证时必填)
  - 需求:所在地址(到街道/小区级,发布时必填)
- 需求地址发布时用腾讯地图 geocoder 转经纬度落库(前台不展示坐标),用于老师端"按距离筛选"计算
- `getLocation`(精确)若申请被拒 → 降级为"按区筛选",业务上按区找老师已够用

### 9.3 动态墙(两端广场页顶部,已入 MVP)

- **位置确认**:家长端=简历广场页顶部;老师端=需求广场页顶部。**不单独设首页 Tab**
- **实现方式:订单状态的只读投影,不新增动态表、不生成动态记录**
- 数据源:订单表 `status IN (2 试课中, 3 已完成)`,join 需求表与简历表,按状态更新时间倒序,limit 20
- 展示字段(**严格脱敏**):区域(仅到区)、学段、科目、状态、相对时间
- **投影禁区:预算/时薪、联系方式、需求 id、任何可反查身份的信息**
- 缓存:Redis 缓存查询结果(短 TTL),订单状态变更时主动失效
- 冷启动兜底:查询结果为空时前端隐藏该模块

## 11. 技术架构

### 11.1 部署

| 层 | 方案 |
|---|---|
| 小程序前端 | **uni-app 开发**(编译微信小程序,与 yudao 生态一致;微信对接代码可参考 yudao mall-uniapp) |
| 后端 | 阿里云 2核4G 单机:**yudao 单体版底座(Spring Boot 3 + MyBatis-Plus)+ PostgreSQL 16(含 pgvector 扩展)+ Redis**(同机部署,内存精打细算) |
| 图片 | 学生证/学信网照片:OSS(复用 yudao 文件上传模块) |
| API | 备案域名 + HTTPS + 免费证书 |
| 管理后台(电脑) | yudao admin-vue3 底座 + 自定义业务页面(审核/订单/评价/举报/反悔/统计) |
| **管理后台(手机审核)** | **yudao admin-uniapp 移动端**,适配自定义审核页面,满足"不在电脑旁随时审核" |

**容量评估**:低频高客单信息流场景,2核4G 撑几万注册用户无压力;瓶颈在冷启动获客,不在服务器。

**模块裁剪原则**:yudao 单体版只保留基础设施模块(认证/字典/文件/定时任务/日志/代码生成),不引入商城/CRM/ERP/支付/短信/工作流/AI/多租户模块。

**耦合底线**:业务逻辑(订单状态机、防跳单脱敏层、订阅消息埋点、认证状态权限矩阵)写在独立 service 层,不深度耦合 yudao 内部机制,保证可剥离可升级。

### 11.2 关键技术点

| 项 | 方案 |
|---|---|
| 登录 | 小程序 `wx.login` → code2session → openid,接入 yudao 社交登录与 token 体系(参考 mall-uniapp 对接代码) |
| 通知 | `subscribeMessage.send` + access_token 定时刷新缓存;43101 静默失败 |
| 站内信 | 复用 yudao notify 模块(system_notify_template/message),单向系统通知,小程序端"消息"页 + 未读角标 |
| 定位 | 腾讯地图 geocoder 转需求坐标;距离计算后端完成,瞬时用即弃 |
| 加密 | 手机号 AES 加密落库 + 统一盐 SHA-256 哈希列(mobile_hash,客服查找),密钥与盐都在环境变量 |
| 定时任务 | 复用 yudao 定时任务模块(每天 8:00 老师确认超时催办 / 每天 1:00 需求超时下架检查) |
| 字典表 | 复用 yudao 字典管理模块(system_dict_data:科目、学段、学历、评价标签;城市/区前端静态数据) |
| JVM | 芋道单体 `-Xmx1G` 起步,`MaxMetaspaceSize=256m`、`-Xss512k`;PG `shared_buffers=256-512M`、`work_mem=4-8M`;Redis `maxmemory 128m` |

## 13. 信息费定价策略(模拟 v0.1,正式定价待定)

> 市场参考:聊城家教网 200-500 元/次固定信息费(不成功全额退);神舟家教按课时工资 20% 提成押金月结;陪读家教网试课成功后收单次课时费 10%。

| 项 | 策略 |
|---|---|
| 定价 | **统一 99 元/单**,一次性信息费,不分学段(冷启动期话术极简) |
| 收费时机 | 老师确认试课后(收费前置,防跳单生命线,不动摇) |
| 退费规则 | 试课失败 → **全额退**;收费后家长放弃(管理端取消)→ **全额退**;收费后老师放鸽子 → **全额退** + 老师记反悔 |
| 客服话术 | "99 元介绍一位合适的家教老师,试课不满意全额退" |
| 定价逻辑 | 低锚点抵消前置收费的心理抵触;对比同行 200-500 元有价格竞争力;试课通过后家长对 99 元不再敏感 |

| 落库 | 订单表**暂不存金额**(定价统一),后期差异化定价再扩展 fee_amount 字段 |
